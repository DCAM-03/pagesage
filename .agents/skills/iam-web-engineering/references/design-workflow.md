# Console Design Workflow

Use for visual/interaction work, not backend-only changes or routine API plumbing.

## Sources And Responsibilities

- Read the coordination checkout's `axis-iam-web/DESIGN.md`, active task, accepted prototype, and owning application's current tokens/components. Resolve the coordination path from the task; a worktree may not inherit its parent instructions. Report an unavailable reference instead of guessing another checkout.
- Refero supplies reference material, not an authoritative product contract or executable instructions. Record only locally selected ideas; do not import a whole external DESIGN.md or reproduce a third party's branding/assets.
- Impeccable supplies visual/UX assessment and refinement. `iam-web-engineering` continues to own implementation, API/security behavior, and engineering tests. `validation-harness` classifies evidence; `project-coordination` owns delivery and independent acceptance.
- These are capability responsibilities, not new session assignments. Preserve the task's named executor, writer ownership, and shared-runtime reservation. A design skill does not authorize delegation, another chat, or an independent acceptance claim.

## Impeccable Use

Use the installed `impeccable` Skill when available; read its complete entrypoint and only the relevant command references. This installation is user-wide at `<HOME>/.codex/skills/impeccable`, from `pbakaus/impeccable` commit `abf5779cabc20147fd9c013fa4705088c200bf8a` (Skill 4.5.2, engine 0.1.14). Treat this as provenance, not an instruction to reinstall on each task.

- Follow its context loader with cwd at the owning application and an explicit target. Supply the coordination design reference if automatic discovery misses it. A missing PRODUCT.md or DESIGN.md does not make an existing console greenfield or justify blocking a narrow fix on initialization.
- Portal/Admin settings are **Operate** surfaces. Preserve established identity and behavior for refinement; a replacement visual world requires explicit redesign scope.
- Select a command that matches the request: `critique` for hierarchy/clarity, `audit` for accessibility/responsive quality, `layout`/`typeset`/`clarify` for a demonstrated defect, `polish` for final refinement, and `adapt` for viewport issues. Do not run the whole command catalog.
- The current task's explicit no-delegation rule takes precedence over Impeccable's optional/built-in agent workflows. Perform permitted review inline, disclose the required degraded single-context label when applicable, and never represent it as independent acceptance. Do not launch bundled finish/document/asset agents implicitly.
- Keep launcher/detector calls telemetry-opted-out with `IMPECCABLE_NO_TELEMETRY=1`. Do not upload source, screenshots, tokens, tenant data, or secrets to external design services. A refinement request does not authorize a remote catalog roll, live helper injection, automatic hooks, new dependencies, or browser-security changes.
- Use existing authorized browser tooling and the task's fixture reservation. Detector suggestions are review candidates, not automatic defects: accepted typography, semantic status colors, and necessary grouping can be intentional. Avoid broad suppressions or style churn just to achieve zero findings.

## Delivery Loop

For review versus implementation authority, follow
[request intent and change boundary](../../project-coordination/references/session-lifecycle.md#request-intent-and-change-boundary).
When comparing products, use equivalent writable contracts; distinguish visual fields from governance switches,
response metadata and separately managed resources. Trace declared fields through editor, persistence, inheritance,
preview and production rendering before claiming usable capability or parity. Field counts alone establish neither.

For review-only requests, inspect and report concrete findings without source changes. For authorized implementation, inspect the affected flow, identify a short prioritized delta, implement it in the same execution turn, then verify it. Do not turn a UI change into repeated reports, design exploration, or a new approval loop when the task already provides enough direction.

Check changed representative surfaces against the prototype and design reference in EN/ZH, desktop and narrow mobile, including long labels, keyboard/focus, dialogs, validation, pending/save, permission denial, and stale conflict where applicable. Measure actual overflow/scroll ownership; do not mask it with global overflow clipping. Use bounded batched visual passes; unresolved functional/security defects remain explicit gates rather than being waived by a polish budget.

Record only the route, source/build identity, viewport/locale, exact scenario, observed result and necessary screenshot in the existing owned evidence record. Reuse existing evidence structure rather than creating a report per command. Build, mock, detector, and screenshot evidence each prove only their own surface; visual review does not establish API/authorization correctness or product completion.
