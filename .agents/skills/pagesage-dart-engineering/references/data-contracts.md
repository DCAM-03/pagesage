# 数据、持久化与兼容

先读 `docs/06-data-model.md` 与实际 `lib/core/database/`、领域模型、受影响 repository。
不从 schema 文档中的版本号推断当前数据库版本，以实际代码与已发布迁移链核对。

## 领域与存储边界

- 领域模型和 repository 契约不暴露 Drift row、Companion、Widget 或平台资源。
- Data 层完成 Drift / JSON 与领域映射；业务 ID、时间、排序和单位保持已有约定。
- 新字段须同时检查 create/read/update/watch、复制、删除关联及适用的导出/备份路径，不能只改表定义。
- 缺字段、显式 null、空字符串和错误类型不是同一含义。仅对已定义历史缺省使用默认值；
  有版本的快照遵循其未知版本处理契约，不能把损坏记录伪造成合法默认对象。
- locator 是可持久化值对象；保留格式对应位置与来源身份。历史恢复不能悄悄换成当前页面定位。

## Drift 变更

1. 检查实际表、`schemaVersion`、upgrade 策略、生成输出和既有迁移测试。
2. 已发布 schema 变化必须增加迁移；不清库、不删除用户书库来获得绿灯。
3. 区分新库、旧库升级和旧数据读取；可空字段不代表可以不测试迁移。
4. 多步写入的原子性由适当事务保证；删除关联和 FTS 一致性须检查真实实现，不能靠 UI 顺序猜测。
5. 用仓库现有生成入口更新 `app_database.g.dart`，不手改生成文件。生成后审查意外大范围变化。
6. 用临时 SQLite 验证关键旧记录、外键/关联、索引和字段语义；持久化恢复类修改增加文件库 close/reopen。
7. 升级测试的历史结构要与目标旧版本对应。不能只在当前表上把 user_version 改小，就当作完整旧库证明。

## 设置和序列化

- settings enum、JSON 名称和时间单位是持久契约。新增值要覆盖旧设置缺字段和新值往返。
- `copyWith` / 更新接口对“保留原值”和“清空字段”语义一致；测试不能只覆盖非空赋值。
- 相同时间戳下若业务依赖稳定顺序，显式保留适当次序，不用随机 UUID 排序冒充写入顺序。
- 查询或解码失败向应用层保留错误，UI 显示失败而不是“没有数据”。

## 文件和隐私

- 文件操作使用跨平台 path / file API，核对 Windows 路径和相对资源解析，不拼接仅对 Linux 有效的路径协议。
- 延续文件导入复制、Markdown 目录只读就地读取和移除不删除原文件的规则；测试使用临时目录。
- 备份、导出和删除检查实际关联数据，不把缓存、API key 或用户源目录混入可删除范围。
- API key 通过 secure storage 读取；测试使用 fake，不修改用户现有密钥或自动调用真实 Provider。
- 数据库、fixture 和截图不使用真实书库；正文与完整 AI context 不进入常规日志。
