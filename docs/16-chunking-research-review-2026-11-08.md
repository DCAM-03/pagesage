> 检索与核验日期：2026-11-08
> 范围：结构切块、层级检索、上下文扩展、证据预算与评测；不是整个 RAG 领域的穷尽综述
> Implementation State：`IMPLEMENTED`（关联算法的第一版；本文其余研究建议未全部落地）
> Validation Evidence：`TOOLING_PASS`（真实 4 本书、34 题 v2 诊断，另有 1 本真实 EPUB、10 题冻结留出及其修复后审计重放；不是 LLM 回答质量、跳转正确率或 E2E）
> 设计入口：[结构感知的父子分块与上下文扩展](15-parent-child-chunking.md)
> 落地进展：本报告中的结构切块、检索原文分离、同父上下文和边界效果对照已有第一版实现；真实源文诊断和 EPUB 冻结留出已完成，监督复核补修了回退截取跨度和未测量指标，运行时重建、跨书泛化和真实跳转仍未验证，详见设计入口。

## 1. 结论与边界

保留「结构分层 + 顺序贪心 + 小块召回 + 按预算扩展」作为第一条基线。近期材料不支持直接把它替换为逐句调用 LLM、强制语义切块或全量树路由。最值得补强的是：检索文本与引用正文分离、受控跨父块扩展、完整证据评测，以及软目标长度和硬上限的区别。

这里要区分已落地与仍待做：当前 `SearchIndexer` 已接入 `StructureAwareChunker`，但用户现有 schema v5 数据库仍是旧 1200 字块，需重建索引后才会使用父子块；版本化快照、章节树候选和本文的其余改进尚未接入。`ContextBuilder.maxSourceChars = 12000` 仍是字符限制，不是 token 窗口。真实离线收益不能外推为模型回答质量已提升。

论文数字只描述各自的数据、模型和预算设置。本次不据此承诺 PageSage 的准确率、内存或响应时间。

## 2. 一手资料与适用性

### 2.1 QESChunker：从问题—证据监督优化静态索引

- 论文：[QESChunker](https://arxiv.org/abs/2610.36557)，首次提交 2026-10-27；本次核验的是预印本，不视为已同行评审结论。
- 核心：使用人工或模型产生的 question–evidence 对构造文档级静态索引，不使用留出的测试问题。非重叠情况下，其特定目标可以用动态规划精确求解；允许重叠时，论文分析了不同的组合优化问题与贪心近似。
- 可借鉴：块质量应看能否在预算内找齐证据，而不只看块长度与主题相似度；可以把不同切块策略作为离线候选比较。
- 暂不照搬：PageSage 没有这些监督数据；合成问题也有额外调用和偏差。论文中贪心算法的理论保证不适用于我们的顺序切块或上下文打包。此次没有核验到可直接接入的作者开源实现，不把论文当成现成依赖。

### 2.2 Adaptive Chunking：按文档选策略，而非所有文档一个配置

- 论文：[Adaptive Chunking: Optimizing Chunking-Method Selection for RAG](https://arxiv.org/abs/2603.25333)，首次提交 2026-03-26，页面注明已获 LREC 2026 接收。
- 作者代码：[ekimetrics/adaptive-chunking](https://github.com/ekimetrics/adaptive-chunking)，MIT。
- 核心：通过引用完整性、块内凝聚性、文档上下文连贯性、结构块完整性、长度合规性五项指标选择切块策略；包含 split-then-merge 等方法。
- 可借鉴：先区分叙述正文、代码、表格、PDF 提取文本等文档特征；贪心切块后允许局部边界修复。
- 限制：指标自身可能需要嵌入或模型调用，不能全当成本地免费规则；本征指标提高也不等价于回答正确。先离线比较少量配置，不在每次提问时重建索引。

### 2.3 SCAR：有条件地扩展邻块

- 论文：[SCAR: Semantic Continuity-Aware Retrieval for Efficient Context Expansion in RAG](https://arxiv.org/abs/2606.16661)，首次提交 2026-06-15，本次页面修订日期为 2026-08-22，页面注明已获 CIKM 2026 短文接收。
- 作者代码：[scarmethod/SCAR](https://github.com/scarmethod/SCAR)。核验到复现实验和数据；仓库根目录未发现许可证文件，GitHub 许可证字段为空，复用代码前仍须确认授权。
- 核心：综合邻块对问题的相关性与连续性代价，使用相对于种子块相关性的阈值决定是否扩展。论文评估采用嵌入表示。
- 可借鉴：父块边界是工程分组，不应该成为证据绝对边界；固定左右各补一块、命中后整父块展开都可能浪费预算。
- 限制：纯 BM25 没有论文使用的同一语义信号，不能直接套其阈值或宣称复现效果。PageSage 第一版可先使用明确的结构续段关系；语义连续性留待嵌入能力与评测具备后比较。

### 2.4 HiChunk：层级结构值得保留，树不是万能过滤器

- 论文：[HiChunk: Evaluating and Enhancing Retrieval Augmented Generation with Hierarchical Chunking](https://aclanthology.org/2026.acl-long.1372/)，ACL 2026；不能据会期推断算法和代码都刚刚发布。
- 作者代码：[TencentCloudADP/hichunk](https://github.com/TencentCloudADP/hichunk)，包含训练、检索和评测脚本。许可证以 MIT 为主，但明确说明所含 Contriever 组件采用 CC BY-NC 4.0，不能把整个依赖树统称为可商用 MIT。
- 可借鉴：同时维护细粒度检索单元与上层结构，单独评估不同层级的检索和上下文构造。论文的结构生成使用微调 LLM，并提出 Auto-Merge 检索，不等同于直接解析现成 TOC。
- PageSage 的取舍：先沿用 EPUB TOC、Markdown 标题和可靠 PDF 结构，保留正文候选旁路；不引入训练流水线，也不因树路由未命中就排除正文。此取舍是工程判断，不是论文对本项目的实测结论。

### 2.5 Docling HybridChunker：补检索上下文，保留原文

- 官方文档：[Hybrid chunking](https://docling-project.github.io/docling/_generated/examples/hybrid_chunking/)、[Chunking](https://docling-project.github.io/docling/concepts/chunking/)。
- 官方代码：[docling-core](https://github.com/docling-project/docling-core)，MIT。
- 核心：结合结构与 token 约束进行拆分、合并；`contextualize()` 可为检索表示补充标题等上下文，表格续段可以重复表头。
- PageSage 可移植规则与元信息设计，第一版不引入 Docling 的 Python 文档处理栈。补充文字应进入检索或发送包装层，不能改写可回跳的原文跨度。

### 2.6 Chonkie：参考规则实现与边界处理，不引入框架

- 官方代码：[feyninc/chonkie](https://github.com/feyninc/chonkie)，MIT。
- 官方文档：[RecursiveChunker](https://docs.chonkie.ai/oss/chunkers/recursive-chunker)，提供基于段落、句子等多级边界的递归分割规则及语言配置。
- 可借鉴：把边界规则和计量器做成可测试的独立组件；中英文标点、Markdown 特殊块分别处理。
- 限制：Python 规则不能直接证明 Dart 定位正确或性能达标；需用原文跨度与本地样本验证。不能只换一个 chunker 类名就宣称效果提升。

### 2.7 PageIndex：借鉴结构导航，修正 SDK 与触发规则的判断

- 官方项目及 Python SDK：[VectifyAI/PageIndex](https://github.com/VectifyAI/PageIndex)，Python SDK 已提供本地与 Cloud 路径；另有 [JavaScript/TypeScript API SDK](https://github.com/VectifyAI/pageindex-js-sdk)。JS 客户端不等于本地 Python 检索实现，两者也都不能直接视为 Dart/Flutter 内嵌实现。
- 可借鉴：用树和节点摘要辅助找到文档区域，回答时仍引用原始正文。现有标题结构并不总是完整、准确，不能因为有 TOC 就认定结构问题全部解决。
- 修正：不能把「建树涉及模型」直接等同于「不允许采用」。自动本地解析、结构索引和模型/联网调用必须分开讨论；本次不修改 AI 设置或触发规则，也不自动上传文件。
- 暂不采用整套服务：PageSage 需要跨格式 locator、离线索引与 Android/Windows 路径；API 客户端本身不解决这些契约。成本需按模型、文档和实际调用记录评估，不能沿用统一每页价格。

### 2.8 两篇补充评测论文：避免把「检索到一点」当成「证据齐全」

- [The Bottleneck Is Retrieval, Not Reading](https://arxiv.org/abs/2610.26951)，2026-10-18；作者提供 [LC-EBG](https://github.com/debobanerjee/LC-EBG) 代码入口。论文区分答案正确与证据支持，指出多事实题中「任一相关块命中」和「全部必需证据命中」有明显差别，也检查文档身份元信息的丢失。可借鉴联合评测口径，不据此改成默认发送整本文档。
- [Structure-Aware Semantic Chunking with Title-Chain Prefixes](https://arxiv.org/abs/2608.00824)，2026-08-01 预印本。作者同时报告标题链方法及评测陷阱：去掉标题后，评审模型可能失去判断相关性所需的信息，前后分数不再直接可比。PageSage 应固定原始文档与证据标注，以源区间评估覆盖；不要按经过不同包装的文本重新生成黄金标签。该文的语义合并仍使用嵌入，零额外 LLM 调用不等于零计算成本。

## 3. 对当前设计的调整建议

以下均为拟议设计，尚未证明有效。P0 表示实现父子分块时一并考虑，不表示已完成。

| 优先级 | 调整 | 解决的问题 | 代价与验收重点 |
| --- | --- | --- | --- |
| P0 | 区分 `sourceText`、`retrievalText`、`contextEnvelope` | 子块离开标题后缺主语；补上下文又污染引用 | 索引元信息与计量增加；引用必须仍回取精确原文 |
| P0 | 同父优先，允许可靠续段关系跨父扩展 | 一段定义、推导或表格恰好被父块边界截断 | 增加关系与跨度列表；不得跨权限、版本或靠序号猜邻接 |
| P0 | 评测最终实际发送的完整证据 | 初始召回命中，但去重/配额/打包后丢了关键一半 | 人工证据标注；检查最终提示词中的引用区间 |
| P0 | 独立软目标与硬上限，增加局部尾块修复 | 现有伪代码只用硬上限，软目标没有实际作用 | 确定性局部调整；不能跨结构边界填满 |
| P1 | 离线比较文档类型的少量切块配置 | 一组参数同时处理中文、代码与 PDF 效果未必稳定 | 配置版本化；调参集与留出集分离 |
| P2 | QES 式监督优化、语义连续性与可选重排 | 进一步优化证据完整性和扩展效率 | 监督数据、模型成本和运行环境；先证明增益再引入 |

### 3.1 三种文本表示

```text
sourceText       = 同一源版本中的原文跨度，定位与引用的权威
retrievalText    = 标题路径 / 结构元信息 + 正文，用于建立检索表示
contextEnvelope  = 实际发送时的来源、标题、必要表头和原文证据
```

第一版优先把标题路径等确定性字段分开建索引、单独评分，再与正文候选融合；不要先把同一章标题复制到每个子块的 BM25 正文里，否则会改变长度归一化和词频。若比较拼接表示，应作为独立检索配置，不能复用原正文统计。

模型生成的说明单独标记为生成元信息，不能拥有假的原文 offset。重复表头、标题路径和来源标签仍计入最终发送预算；同一批子块共享的包装尽量只发送一次。

### 3.2 跨父块不等于跨来源拼成一段

同一文件、同一正文单元、同一小节内，原文连续且具备 `continues` 关系的相邻父块，可以提供有限的跨父窗口。标题变化、文件变化和版本变化不能仅因位置相邻就越过。

表头—表格续段、代码续段等依赖可以建立 `header_of`、`continues` 关系。跨页或不连续证据以多个 `SourceSpan` 表达，分别保留 locator；不能生成从首段到末段的包围引用。缺乏可靠结构映射时不扩展。

每次扩展都受最大关系跳数、候选总数及最终输入预算约束；具体数值待评测。本地结构续段信号和后续语义分数分开记录，不把启发式信号叫作 SCAR 的复现。

### 3.3 贪心之后做小范围修复

先复用同一份结构单元、原文跨度和安全切点，再分组父子块，不为每种分组重新生成正文。软目标用于选择合适切点，硬上限用于拒绝过长候选，二者必须分别参与决策。

若末块过短，只检查前一个块：合并后合规则合并；否则尝试移动一个完整单元，使边界两侧更平衡。不能为修复尾块跨文件、小节或破坏表格/代码依赖；无法改善就保留短块。此为待消融的局部启发式，不承诺全局最优。

tokenizer 对拼接文本的计数不一定等于各片段计数之和。最终上限以实际候选表示重新计数。极端情况下，单个不可分割字素簇已超过硬上限，应明确报错并停止发布该索引版本，不能同时声称保留字素、完整覆盖且始终不超预算。

## 4. 修订后的算法链路

```text
源文件快照与 locator 映射
  → 结构单元 + 原文跨度 + 续段/依赖关系
  → 父块顺序分组 → 父内子块 → 可选局部尾块修复
  → 正文索引 + 独立结构字段索引
  → 完整性检查 → 原子发布同一索引版本

问题 + 允许范围 + 输入预算
  → 正文候选 ∪ 结构候选（后续可并入语义候选）
  → 融合、去重、问题各方面的候选证据
  → 子块 / 同父窗口 / 父块 / 有界结构续段窗口
  → 在最终预算内选择，保留比较对象与连续证据
  → 对真实发送文本计量、去重和来源核对
  → 回答 + 实际证据引用 + 未覆盖说明
```

继续使用 Drift/SQLite：章节、父子块、快照、结构元信息和有向关系都是可事务更新的业务数据。新增关系可采用带 `snapshot_id` 的关系表，确保两端属于同一版本与允许来源；确切 schema 在实现时同步数据模型并迁移。暂不引入 DuckDB、Python 服务或新向量数据库。此数据库选择是基于本项目现状的工程建议，不是上述论文的实验结论。

## 5. 怎样判断优化是否真的有效

最小评测先用 30–50 个有人工证据的问题做冒烟和诊断，不能视为统计上充分的效果证明。至少包括：中文定义、标题命中、同义改写、跨父边界推导、表格续段、中英代码、两侧比较、无答案及文件更新。

每个问题标注一个或多个可替代的完整证据集合，每个集合包含若干必需原文区间。完整覆盖任意一组即可，不能要求把所有替代表述同时找齐。多文件题按版本与 locator 标注；模型生成摘要不能充当黄金原文证据。

| 层面 | 指标 / 检查 | 要排除的误判 |
| --- | --- | --- |
| 解析与切块 | 正文覆盖、原文回取、结构完整性、硬预算、极端字符失败策略 | 块看起来完整，但文字丢失或引用错位 |
| 候选 | 固定 K 及固定 token 预算下的证据覆盖、完整证据召回 | 只命中一半，就被记为正确召回 |
| 最终发送 | 完整证据集合覆盖、比较对象覆盖、无关与重复 token、真实输入预算 | 初始召回很好，最终打包却挤掉关键证据 |
| 回答 | 有来源支持的正确性、无答案拒答、引用定位、人工核对 | 只检验引用编号存在，误称事实已经核验 |
| 工程 | 索引耗时、磁盘增量、峰值内存、查询 p50/p95、模型调用量 | 把 Python 论文耗时当成 Dart/Android 性能 |

对照顺序：当前代码 → 原设计的父子贪心 → 加结构元信息 → 加受控扩展 → 加尾块修复。保持源版本、问题、检索器、模型、输入预算一致，逐项消融；监督/参数选择只用调参文档，另留未参与选择的文档和问题验证泛化。

运行时没有黄金答案，不能凭评分器判断「已经找齐」。只能记录检索来源、扩展理由、预算与覆盖代理信号；真实完整证据指标由离线标注评测计算。

比较标题包装策略时，评审者使用一致的原文、必要身份/结构元信息和固定标注协议；检索器各自只使用配置允许的表示。不能一边删除用于消歧的上下文，一边把评审分数变化全部归因于切块质量。
